# V4.1 제작·검증 결과

## 결과와 확인 순서

공식 Rive CLI 1.8.0로 실제 편집 가능한 RML, 두 테마 로컬 `.riv` 실행 프로젝트, 최종 MP4를 제작했다.
V4의 **16초·5개 장면·모바일 9:16·다크/라이트·사이트 토큰·추천 상태·브랜드 마무리**를 유지했다.
작업 브랜치는 `amlyhbf/my-gorithm`의 `feat/rive-intro-v4-1`이다.

먼저 다크 최종 MP4를 본 뒤, 모핑 전후 비교(6–10초), 이동 전후 비교(0–6초)를 확인하면 된다.
비교 영상의 왼쪽은 V4, 오른쪽은 V4.1이고 같은 시각을 맞췄다.
스토리보드·연속 스틸·곡선과 수치를 함께 검토했으며, 이 환경에서 실물 휴대폰이나 브라우저 통합 재생을 검사한 것은 아니다.

## 실제 미디어 검사

FFprobe로 디코딩 프레임 수, 프레임 타임스탬프, 코덱, 해상도, 길이와 파일 크기를 검사했다.
단순히 MP4의 FPS 태그만 확인하지 않았다. 모든 최종 파일은 H.264 / yuv420p이며 오디오는 없다.
MB 표기를 쓰는 안내에서는 1 MB = 1,000,000바이트다.

| 파일 | 해상도 | FPS | 길이 | 디코딩 프레임 | 파일 크기 | 전체 비트레이트 |
| --- | --- | --- | --- | --- | --- | --- |
| `intro-v4-1-dark.mp4` | 1080×1920 | 60 | 16.000초 | 960 | 3,435,603바이트 | 1,717,801 bit/s |
| `intro-v4-1-light.mp4` | 1080×1920 | 60 | 16.000초 | 960 | 4,069,039바이트 | 2,034,519 bit/s |
| `compare-motion-0-6.mp4` | 1080×1040 | 60 | 6.000초 | 360 | 891,511바이트 | 1,188,681 bit/s |
| `compare-morph-6-10.mp4` | 1080×1040 | 60 | 4.000초 | 240 | 867,597바이트 | 1,735,194 bit/s |

각 MP4의 프레임 타임스탬프는 `n/60`과 오차 0.000001초 이내였다.
정확한 값·SHA-256은 [final-media-verification.json](final-media-verification.json)에 있다.
GIF는 360×640, 15 FPS를 목표로 추린 확인용 파일이다. GIF 시간 단위·색상 수·정적 프레임 합치기 특성 때문에
최종 움직임과 색상을 판단할 때는 60 FPS MP4를 사용한다. 실측은 [gif-verification.json](preview/gif-verification.json)에 있다.

## 60 FPS 원본 프레임의 출처

- 각 테마 0–10초: 1/60초마다 공식 CLI `--screenshot`, `--advance=프레임+1`로 새로 캡처한 Full HD 600장.
- 각 테마 10–16초: V4의 원래 네이티브 60 FPS PNG 360장을 보존. 저프레임 영상에서 만든 중복 프레임이 아니다.
- 보존 전 객체·색·폰트 구조, 10초 이후 수치 속성을 검사했다. 다크·라이트의 10/12/14/15.983초 실제 RGB 렌더 8개도 V4와 차이 0이었다.
- 프레임 0–599는 테마별 600장 모두 PNG 해시가 다르다. 뒤의 의도적인 UI 단계·브랜드 읽기 구간은 정적 유지가 있다.
- 최종 테마별 960장의 크기가 모두 1080×1920이며 원래 suffix와 실제 파일도 일치했다.

[프레임 감사](preview/frame-audit.json), [보존 구간 증거](preview/suffix-verification.json)를 보관했다.
네이티브 PNG와 별개로, 손실 압축한 서로 다른 MP4의 픽셀이 완전히 같다고 주장하지 않는다.

## 개선과 자체 수정

| 검토 항목 | 구현·검토 근거 | 판단 |
| --- | --- | --- |
| 이동의 자연스러움 | 공통 주기 궤도 대신 4개의 서로 다른 C2 경로. 출력 값 베지어가 위치뿐 아니라 입·출구 미분값을 연결 | 구간 접합 속도 변화 감소, 전체 길이는 그대로 |
| 모핑의 유연함 | 선두·후미 0.19–0.27초 지연, 다른 단면 두께와 핸들, 감쇠 회전 | 부분별 변화가 늦게 따라오는 중간 형태 제공 |
| 윤곽 결함 | 첫 스틸에서 짧은 몸체의 안쪽 접힘 발견. 중심선 미분과 반경을 계산하고 곡률×반경을 제한하도록 수정 | 수정 후 2,404자세의 평탄화 윤곽에서 자기교차 0 |
| 공간 곡선의 연결 | 8개 같은 벡터 꼭짓점과 핸들을 계속 애니메이션. 캡·몸체 접선 동시 계산 | 측정 최대 접선 불일치 약 0.000153도, G1 범위 |
| 교차와 합류 | 합류 조각이 예전 좌표로 향하는 문제를 찾아 새 경로 추종으로 수정. 잔상도 새 궤적을 0.09초 지연 추종 | 본체와 보조 요소의 위치 관계 정리 |
| 전체 이야기·리듬 | 0–3/3–6/6–10/10–13/13–16초 구조 보존, 새 움직임을 앞부분에 배치 | V4를 느리게 재생한 버전이 아님 |
| 관심도 통제 의미 | 기존 조절·추천 장면을 유지하고 실제 사이트 함수로 22개 상태 재계산 | 카드 수·순서·추천 비율 모두 V4와 일치 |
| 브랜드 가독성 | 동일한 마지막 포즈·문구와 버튼 공간, 세 모바일 크기의 정적 시안 | 제목·보조 문구 유지, 실기기 테스트 별도 |

위치 키 접합의 최대 속도 변화는 V4 약 643–821px/s에서 V4.1 0.002px/s 미만으로 측정됐다.
각 버전의 자체 접합점에서 입·출구 속도를 비교한 수치이며, 경로와 접합점 개수는 서로 다르다.
최고 속도가 낮아졌다는 의미가 아니다. 빠른 통과와 느린 정돈을 구분해 전체를 느리게 만들지 않았다.
실제 [RML 분석](preview/motion-analysis.json), [곡선 그래프](preview/motion-curves-comparison.png),
[주요 키 변경](keyframe-changes.md), [전후 보드](preview/storyboard-before-after.png)를 남겼다.

근사는 성분별 검색 목표를 두었지만 17점 재측정에서 일부 구간이 이를 소폭 넘었다.
최대 좌표 오차 0.687px, 핸들 길이 0.607px, 핸들 각도 0.003355rad(약 0.193도)를 공개한다.
이 수치는 전 시간의 수학적 오차 상한이 아니다. 실제 출력 윤곽·접선·화면 범위 검사와 같이 판단했다.
수치적으로 매끈하다는 사실만으로 예술적 완성도를 보장하지 않으며, 최종 감상·디자인 승인은 사용자 검토 대상이다.

## 모바일·테마·디자인 보존

360×640, 390×844, 430×932 크기로 두 테마의 조절·브랜드 장면을 `contain` 배치해 잘림을 확인했다.
9:16보다 긴 화면에는 여백을 두고, 영상을 `cover`로 확대해 자르지 않았다.
360px 폭에서 제목은 명목 약 27.3px, 보조 문구는 16px다. 주요 제목·분야명·조절값은 확인할 수 있다.
눈금의 작은 보조 문자는 V4 크기를 유지하므로 실물 모바일 통합 때 확대 여부를 따로 검토해야 한다.
폰 이미지와 [정적 배치 검사](preview/mobile-layout-check.json)는 실기기 터치·성능 검증을 대신하지 않는다.

기존 디자인 토큰과 Pretendard 600/800 폰트 파일은 V4와 바이트 단위로 같다.
다크 페이지 `#090D16` / 카드 `#0F172A` / 본문 `#F8FAFC` / 보조 `#94A3B8`,
라이트 페이지 `#F8FAFC` / 카드 `#FFFFFF` / 본문 `#0F172A` / 보조 `#64748B`를 유지했다.
공부 `#4F46E5`, 기술 `#0284C7`, 문화 `#BE185D`, 취미 `#059669`도 실제 사이트 색 그대로다.
`design-tokens.json`에 테마를 분리하고 Dark/Light 아트보드에 같은 모션 리그를 적용했다.

## 추천 로직과 사이트 보호

실제 `script.js`의 배정·선택 함수를 격리된 Node VM에서 읽기 전용 실행했다.
22개 상태의 실제 카드 ID 순서와 배정 결과가 저장된 V4 시나리오와 일치한다.
독립 0–100/step 5 관심도, 시작 50/50/50/50 → 카드 3/3/3/3,
최종 100/30/20/50 → 비율 50/15/10/25%와 카드 6/2/1/3을 유지했다.
영상의 추천 타일은 실제 선택 분야를 요약하는 그래픽이며 새로운 추천 기능을 구현한 것은 아니다.

`protected-baseline.json`의 원본 영상·소스·사이트 파일 SHA-256이 모두 일치했다.
새 V4.1 폴더와 새 도구만 작업 브랜치에 추가했다. 운영 Firebase 배포·원본 저장소 수정·기존 브랜치 병합은 수행하지 않았다.
[로직·보호 검사](preview/logic-verification.json)에서 근거를 확인할 수 있다.

## 기술적 한계와 다음 단계

- 공식 CLI verify/inspect는 최종 소스에서 오류 0·경고 0이었다. 로컬 네이티브 캡처가 실제로 동작했다.
- 이동 설계는 C2지만 출력 값 베지어는 C1 근사다. 공간 윤곽은 G1이며 전 구간 G2라고 주장하지 않는다.
- 감쇠 2차 회전·사전 계산한 시간 지연을 RML 곡선으로 구현했다. 실제 유체 물리 엔진이나 네이티브 spring 기능을 호출한 것은 아니다.
- 기존 방사형 그라디언트 빛과 방향성 잔상을 유지했다. 3D, 물리 입자, 셔터 기반 블러는 구현하지 않았다.
- `.riv`는 실제 로컬 빌드 파일이고 MP4와 다르다. `.rev`는 공식 CLI 로그인 필요로 생성하지 않았다. 웹 런타임·실물 폰 성능은 검증하지 않았다.
- 세밀한 핸들 곡선으로 RML과 런타임 크기가 커졌다. 실제 웹 연결 때 파일 로딩과 실행 성능을 측정해야 한다.
- 디자인 승인 후 반응형 배치, 저장 테마 선택, 첫 방문/다시 보기, 건너뛰기, HTML 시작 버튼, 종료·로딩 오류 폴백, 움직임 감소를 별도 구현해야 한다.

진행·문제 수정·최종 출력은 [WORK_LOG.md](WORK_LOG.md)에 기록했다.
